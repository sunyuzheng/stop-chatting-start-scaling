Introduce the demo as a policy change across a tiny but real system. The point is not code sophistication. The point is that the task requires context, execution, consistency, and a second round of change. That is why it is a good agent demo.

Problem

Hardcoded drift

This is where chat stalls: it can suggest where to edit, but it does not leave behind a better system.

Show the starter repo here. The audience should see one business rule duplicated across checkout, email, help center, and docs. Stress that this is exactly the kind of change work that keeps happening in real teams. The problem is not changing text. The problem is changing the system safely.
Live Prompt

What I ask the agent to do

Implement the policy change across the repo.

  • update the oversized shipping promise to 3-5 business days
  • preserve the Prime exception for the top 20 metro areas
  • remove scattered hardcoded copy
  • create one shared policy source
  • update tests, run them, and fix failures
What Chat Can Do

Give advice, sample code, and likely edit locations.

What The Agent Can Do

Read the repo, apply the edits, run checks, and leave a cleaner architecture behind.

Read the request in business language. Then make the contrast explicit: chat can suggest, but the agent can inspect the repo, implement, test, and repair. This is the slide to set up the live action in Cursor.

Compounding

The second request is the real demo

Follow-up Request
  • expand the Prime metro exception from top 20 to top 40
  • add a remote-state exception for Alaska and Hawaii
The Point

If the first run was only a patch, the second change is expensive again. If the first run created structure, the second change is cheap.

That is compounding.

This is the real proof slide. The first request is not enough. The second request reveals whether we created structure or just patched files. If the second change is cheap, then the system improved. That is the definition of compounding in this talk.
